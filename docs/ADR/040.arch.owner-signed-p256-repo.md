## Context

`docs/phase5.md` 盘点"普通 bsky 用户能用、本项目不能"的能力时，最大的缺口是"客户端接入"：普通 PDS 在服务端持 repo key 并实时签名，所以官方 bsky.app / 任何客户端都能写；本项目是静态 journal + CLI 本地签名，写路径只有 CLI（ADR-014），且 Worker 永不持私钥（ADR-005）。

2026-11-09 的关键发现：**WebCrypto 原生支持 P-256 ECDSA，而 atproto 原生支持 P-256 repo 签名密钥**（`@atproto/crypto` 的 p256 plugin、indigo 的 `atcrypto`、官方 interop fixtures 都已确认）。于是出现一条介于"静态 CLI 发布"和"完整 PDS（私钥上 Worker）"之间的路线：

- 浏览器/CLI 在本地构造 MST + commit v3，用 **owner 自己的 P-256 key** 签名；
- Worker 只做验签、按 per-DID head 追加、广播 firehose、响应读请求；
- **Worker 永不持有私钥**，owner 对数据和 commit 有完全控制，Worker 退化为"纯通道 + 活账本"。

### 协议事实（本地 atproto/indigo 源码确认）

1. P-256 是一等公民：`thirdparty/atproto/packages/crypto/src/plugins.ts` 同时注册 p256 + secp256k1；`ATPROTO_VERIFICATION_METHOD_TYPES` 接受 `Multikey`/`EcdsaSecp256r1VerificationKey2019`/`EcdsaSecp256k1VerificationKey2019`。
2. 签名格式两种曲线一致：64 字节紧凑 `r||s`、**必须 low-S**、禁止 DER；签名前像是无 `sig` 的 commit 规范 CBOR 的 SHA-256；commit 编码/字段序不变（ADR-020）。
3. 公钥是 Multikey：P-256 用 multicodec `0x1200`（varint `[0x80,0x24]`）+ 33 字节压缩点 + base58btc `z`，即 `zDna...` / `did:key:zDna...`。
4. **协议只验 head commit**：`verifyRepoRoot` 只 `ReadableRepo.load(storage, head)` 然后验一个 commit 的签名，不遍历 `prev`；参考实现 v3 commit 的 `prev` 恒为 `null`；relay/appview 对实时事件也只验事件里的 commit。因此**轮换密钥不需要重签历史**。
5. **没有标准的"提交预签名 commit"写端点**：`createRecord`/`applyWrites` 收的是记录，`importRepo` 是整包 CAR 导入且默认不验签。所以：
   - 自有 Web 客户端走自定义 append 端点（M1）；
   - 官方 bsky.app 仍然需要 Worker 持 repo key 服务端签名（M2/M3，另一条产品线）。

### Spike 结果（`.tmp/p256-spike/REPORT.md`）

- Node 22 + Edge 157 的 WebCrypto P-256 签出的 64 字节 low-S 签名，被官方 `@atproto/crypto@0.5.7` 接受；
- 用现有 `src/shared.js` + `cli/mst.js` 构造的 commit/CAR，被官方 `@atproto/repo@0.11.4` 的 `verifyRepoCar()` 接受（DID、签名、MST、record leaf 全过）；
- high-S 被官方拒绝；DER 被拒绝；压缩公钥用 BigInt 解压到 65 字节的路径验证通过；
- 真实账号旋转后，`verifyRepoCar` 对新 head + 全量 CAR 仍返回 true。

## Decision

采用 **M1：owner 自签 + Worker 活账本/纯通道**，并立即把主账号从 K-256 轮换到 P-256。M3（官方客户端兼容）作为后续可选阶段。

### 1. 密钥与签名

- 新账号默认 P-256；现有账号通过 `seal.js rotate-key --curve p256` + `rotate-head` 轮换。
- 私钥只在 owner 的浏览器/CLI：浏览器用 WebCrypto（non-extractable 或口令加密的 JWK），CLI 用 PKCS#8；Worker 永不持有。
- 网络写只接受 P-256；K-256 旧事件继续可读，CLI 仍可验证（per-event `signingKey` + `previousPublicKeys`）。
- low-S 在签名端归一化；验签端显式拒绝 high-S（WebCrypto verify 单独使用会接受 high-S）。

### 2. 写路径（append）

- 自定义端点 `POST /xrpc/com.atproto.worker.appendEvent`，body `{event}`。
- Worker 校验：字段/NSID/rkey、record CID、commit CID、`commit.did/rev/version/data`、`commit.prev == head`、`rev > head.rev`、P-256 签名、CAR root/commit/record/MST-root 存在性、大小限制。
- Firehose DO 用 SQLite `events`/`heads`/`meta` 做原子 head CAS + 追加 + firehose 广播；`commitCid` 唯一，重复 POST 幂等。
- 成功后 `notifyRelay(env, handle)`；新事件立刻被读端点看到。
- 两设备并发写：后到者 409，客户端拉新 head、rebase、重签。

### 3. 读路径

- 主源：DO `/snapshot`（JSON 行，按 seq 排序）；ASSETS / `JOURNAL_CONTENT` 只作为 fresh deploy 的 seed/fallback。
- `Journal.load()` 先用模块级缓存（key = max seq），避免每请求全量传输/校验；`getRecord`/`listRecords`/`getRepo`/`getLatestCommit` 语义不变。
- 读路径**仍然不验签**（ADR-030 的信任边界保留）；append 时验一次，历史由 seed/CLI/之前的 append 负责。

### 4. 账本与 schema

- 复用现有 `Firehose` DO（已 `new_sqlite_classes`），不新增绑定/迁移。
- 表：`events(seq PK, did, collection, rkey, op, rev, commit_cid UNIQUE, record_cid, time, json)`、`heads(did PK, commit_cid, rev, seq, mst_root)`、`meta`。
- **`offset` 语义升级为全局逻辑 seq**（不再是文件字节偏移）；seed 保留静态 journal 的 offset 作为 seq，新 append 用 `max(seq)+1`。
- 新 journal 行加 `v: 2` 与 `signingKey`（该事件签名的 Multikey）。旧 v1 行继续可读。
- seed：ledger 为空时从 `public/journal.ndjson` 一次性导入；之后静态文件只做 seed/备份，绝不覆盖活账本。

### 5. 身份与轮换

- DID 文档 `verificationMethod[#atproto]` 用 `type: "Multikey"` + P-256 `zDna...`；DID 文档参数化，移除硬编码 K-256 fallback。
- 轮换：发布新 did.json（P-256）→ 用 P-256 签一个新 head（`data` 可保持原 MST root，`prev` 指向旧 head）→ 之后都用 P-256。协议只验 head，**历史不需要重签**。
- 主账号推荐同一次部署带上新 `did.json` + 新 journal（避免"did.json 已是新钥、head 还是旧钥"的窗口）。
- relay/appview 有 identity 缓存；发布后可能需要几分钟生效。relay 的 firehose cursor 通常已越过旧事件，不会重新验旧 K-256 事件；若从 -1 重放，旧事件可能因当前钥已是 P-256 而验签失败——这是协议层面的轮换边界，记录为已知限制。

### 6. 客户端

- **静态 Web UI**：`public/app/`（源码 `app/`，esbuild 打包）。支持生成/导入 P-256 key、口令加密存储、导出备份、读 repo、post/delete、409 重试。
- **CLI**：`init --curve p256`、`rotate-key`、`rotate-head`、`push`/`pull`（`--remote`/`--account`）。
- `push` 把本地已签但 ledger 没有的事件 POST 上去；`pull` 把 ledger 快照拉回 `journal.ndjson` + `public/journal.ndjson` 并重建 `.repo-state.json`。
- 规则：ledger 上线后，**不要再用"本地 append + deploy"作为写路径**；所有运行时写入走 append（浏览器或 `seal.js push`），静态文件只做 seed/备份。

## Architecture

```
静态页面（可独立托管）                     Worker                         Firehose DO (SQLite)
P-256 key (IndexedDB, 加密)  ── append ──▶  验签/CID/head CAS  ──────────▶  events / heads / meta
读 getRepo/getRecord         ◀── snapshot ─  Journal 读模型        ◀─────────  snapshot / backfill
                                      │
                                      └── subscribeRepos / requestCrawl ──▶ relay / appview
```

## Consequences

优点：

- 私钥永不离开 owner；Worker 被攻破也不能伪造 commit（只能审查/丢弃/重放）。
- Web UI 可即时写，无需 CLI/deploy；同时保留 CLI 作为自动化/批量入口。
- 保留 ADR-002 的事件溯源、ADR-004 的 CID 链、ADR-020 的 commit 编码；ADR-005 完整保留。
- P-256 让 Worker 验签零依赖、只在 append 时付一次成本。
- 轮换成本极低（只换 head + did.json，历史不动）。
- 账本/读模型/firehose 是 M3（官方客户端）的地基。

缺点 / 风险：

- **仍然不是完整 PDS**：官方 bsky.app 不能登录发帖；要官方客户端必须 M3（Worker 持 repo key + sessions/JWT + 服务端签名）。
- Worker 能审查/丢弃/重放（不能伪造）；owner 需要 `pull`/本地备份来发现。
- 页面托管是信任边界：Worker 托管签名页时，被攻破的 Worker 可替换 JS 把已解锁的 key 当签名 oracle；最强形态是独立静态托管 + CSP/审计。
- `offset` 语义变化需要文档/迁移；seed 与 live 双写会分叉，必须遵守"ledger 上线后只走 append"。
- 完整 MST 路径验证、per-DID 写限流、自注册准入、blob 上传仍未做。
- relay 从 -1 重放旧 K-256 事件可能验签失败（轮换边界）。

## Migration

主账号（2026-11-09）：

1. `node cli/seal.js rotate-key --curve p256`：备份 `config.json.bak`、生成 P-256、重写 `public/.well-known/did.json`。
2. `node cli/seal.js rotate-head`：用新 key 对当前 MST root 重新签一个 head（同内容 update，无新帖），追加 v2 journal 行。
3. `node cli/seal.js validate`：6/6 事件通过（旧 K-256 用 `previousPublicKeys`，新 P-256 用 `signingKey`）。
4. 官方 `verifyRepoCar` 对新 head + 全量 CAR 返回 true。
5. 待部署：`npx wrangler login && npm run deploy`（当前 wrangler 未登录）。部署后首次 append/refresh 会把静态 journal seed 进 DO。

新账号：`seal.js init --curve p256` 或页面生成 → 发布 did.json → 首条 append。

## Alternatives

| 方案 | 说明 | 未选原因 |
|---|---|---|
| M0 外部可写静态 journal | 浏览器写 GitHub，Worker 只读 | 依赖第三方写权限/token；firehose 需轮询 |
| M2 完整 PDS | Worker 持 repo key、sessions/JWT、服务端签名 | 推翻 ADR-005，工程量大；本阶段不需要 |
| M3 混合 | M2 + owner rotation key/did.json 撤销 | 作为后续阶段保留；先完成 M1 地基 |
