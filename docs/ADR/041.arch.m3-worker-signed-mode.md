## Context

M1（ADR-040）解决了"owner 自签 + Worker 活账本/纯通道"，但标准客户端（官方 bsky.app）的写端点收的是**记录**，不是预签名 commit；客户端不会交出 repo 私钥。要让官方客户端可用，PDS 必须在服务端构造 MST/commit 并签名。

`docs/phase7.md` 定义了 M3 的目标、key custody 权衡和分阶段计划。本 ADR 记录 M3 第一刀的实际决策：**每账号一个 mode；worker-signed 账号由 Worker 持有 P-256 repo key，提供 sessions/JWT + 标准写端点 + blobs；M1 的 owner-signed 账号继续保留。**

## Decision

### 1. Per-account mode

- `accounts.mode ∈ {'owner-signed', 'worker-signed'}`。
- 同一账号的 DID 文档只有一个 `#atproto` repo key：
  - `owner-signed`（M1）：key = owner 浏览器/CLI；`appendEvent` 可用；官方客户端不可用。
  - `worker-signed`（M3）：key = Worker 的 P-256 repo key；标准写端点可用；`appendEvent` 的 owner key 不再匹配 DID 文档。
- 切换 mode = 轮换 repo key + 新 head + 发布新 did.json；不是运行时开关。

### 2. 账号与 session

- `accounts`/`repo_keys`/`sessions` 表在 Firehose DO SQLite（additive）。
- `com.atproto.worker.bootstrapAccount`（owner-only，`BOOTSTRAP_TOKEN`）生成 P-256 key、存 PKCS8、设置密码、返回可发布的 did.json；幂等，默认不重置密码。
- 密码：PBKDF2-SHA256，210k 迭代，16 字节 salt，常量时间比较。
- JWT：HS256，`JWT_SECRET`；access 2h、refresh 90d；claims `iss/aud/sub/scope/iat/exp/jti`，scope `com.atproto.access` / `com.atproto.refresh`；refresh 轮换并在 `sessions` 表按 jti 撤销。
- 端点：`createSession/getSession/refreshSession/deleteSession`；错误形状遵循 XRPC。

### 3. 标准写端点

- `createRecord/putRecord/deleteRecord/applyWrites`。
- 流程：`requireAuth` → mode 检查 → 从 ledger 重建 repo（合并事件 `blocksB64`，加载最新 head/MST）→ 应用写入 → 用 Worker repo key P-256 签名 → `POST /append`（head CAS）→ 广播。
- `swapCommit`/`swapRecord` 映射到 head/record CID 校验；失败返回 `InvalidSwap`。
- `applyWrites`：一次 MST 事务 → 一个 commit；ledger 行带 `writes` 摘要（含每条 record/CID），Journal 索引与 firehose `ops` 按多 op 展开。
- repo key：当前单账号实现存 DO SQLite（PKCS8 base64）。生产可改为 Worker secret 或外部 KMS；这一层的取舍见 phase7。

### 4. Blobs

- `uploadBlob`（5 MB 上限，raw-codec CID）+ `getBlob`/`listBlobs`。
- 存储：R2（`env.BLOBS`）优先；没有 R2 时用 DO SQLite（2 MB base64 行上限）作为本地/小文件 fallback。
- `getBlob` 先查 ASSETS（M1 静态 blob），再查 R2/DO；新账号在首条记录前也能读自己的 blob（hosted = ledger ∪ accounts）。

### 5. 范围

- 第一刀只做**单账号 worker-signed**；主账号（现有 did:web）继续 M1 owner-signed，不自动切换。
- 不做公开注册/多租户；`bootstrapAccount` 需要 owner token。
- 不做完整 lexicon 校验、PLC rotation、KMS；这些是后续阶段。

## Consequences

优点：

- 官方客户端（bsky.app）具备登录/发帖/图片的协议路径；数据仍落在自己的 Worker/DO。
- 复用 M1 的 ledger/read/firehose；M3 只新增 auth + server-side signing + blobs。
- 每账号 mode 让 M1 的"owner 完全控制 commit"和 M3 的"官方客户端"共存，不做二选一的全局取舍。
- Worker 被攻破的影响被限制在 worker-signed 账号；owner-signed 账号不受影响。

缺点 / 风险：

- **worker-signed 账号的 Worker 可以伪造 commit**（轮换前）；这是 M3 的固有权衡。owner 的控制点变成 did.json/rotation。
- repo key 存在 DO SQLite（当前实现）；DO/Worker 被攻破即失守。生产应评估 Worker secret/KMS。
- `JWT_SECRET`/`BOOTSTRAP_TOKEN` 是新增 secret；一键部署需要额外配置。
- access token 在过期前仍可用（logout 只撤销 refresh）；如需即时失效，需要每请求查 session/短 TTL。
- 完整 MST 路径验证、per-DID 限流、公开注册、轮换演练仍未做。
- 主账号仍 M1；要让它支持官方客户端，需要显式的 mode 迁移 + did.json 换钥。
