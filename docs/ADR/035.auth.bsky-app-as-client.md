## Context

用户设想：用自己的域名（did:web）**登录官方 bsky.app**，在 app 里发帖，数据存在自己的 PDS —— 用 bsky.app 替代 `seal.js` 作为发帖界面。

### 机制调研（本地 atproto-reference 源码确认）

bsky.app 客户端与 **AppView**（public.api.bsky.app）通信；AppView 的 `com.atproto.*` 目录**没有** createSession / createRecord 处理器（只有 admin/identity/label/temp 与 getRecord），而 **PDS**（packages/pds）才有完整实现：`server/createSession.ts`、`repo/createRecord.ts`、`putRecord.ts`、`deleteRecord.ts`、`applyWrites.ts`、`uploadBlob`。

结论：**登录与发帖由 AppView 代理到用户自己的 PDS 执行**。这正是自托管 PDS 的标准用法（如 pds.plc.xyz 用户可直接用官方 app 发帖，数据落自己的 PDS）。

### 我们的 PDS 现状对照

| PDS 侧所需 | 现状 |
|---|---|
| DID 文档含 atproto_pds 服务 + describeServer | ✅ 已有（relay 收录验证过） |
| sync/read 端点（getRepo 等） | ✅ 已有 |
| createSession / getSession / refreshSession（密码 + JWT） | ❌ 无（无密码、无会话） |
| createRecord / putRecord / deleteRecord（JWT 鉴权） | ❌ 全部 501（ADR-014 设计如此） |
| uploadBlob + blob 存储 | ❌ 无 |
| **服务端签名**（写时构造 commit v3 并签名） | ❌ **私钥只在本地（ADR-005），Worker 从不签名** |

## Decision

**方向可行，但"bsky.app 替代 seal.js"不是零成本复用 —— 它等于把方向 A（客户端写路径）做完整**，且有三个硬前置，其中两个触及本项目最根本的架构决策：

1. **会话认证**：createSession/getSession/refreshSession + 密码（哈希存 DO storage/SQLite）+ JWT 签发（服务密钥，wrangler secret）。
2. **写端点 + 服务端签名**：createRecord 时 PDS 要**自己构造 commit v3、用账号私钥签名、更新 MST、产 CAR blocks**。协议不允许客户端提交预签名 commit —— **私钥必须上 Worker**（secret 存储），这**推翻 ADR-005** 的"私钥仅在本地"安全模型。这正是参考 PDS 的形态（单用户自托管，私钥在 PDS 侧）—— 风险等价于"Worker 被攻破 = 帖子可被伪造"，对单用户个人 PDS 是可接受的权衡，但必须显式决策。
3. **可变账本**：运行时写入需要可追加的账本 —— 静态资产 journal 降级为 seed/快照，**Firehose DO 的 SQLite 成为活账本**（DO 已是 `new_sqlite_classes`）。"单一事实来源"从静态文件变为"DO 账本 + 静态 seed"，连锁影响 ADR-002/014/033（schema 版本化在此落地，见 ADR-033）。

**有利条件**：地基已具备 —— Firehose DO 自带 SQLite 与广播路径；`commitToCbor`/MST/CAR/TID 全套在 cli/ 可移植到 Worker；`@noble/secp256k1` 已在 devDependencies（cli/crypto.js 在用，浏览器/Worker 通用）。参考 PDS 即此形态，方案已被生态验证。

**决策**：本 ADR **记录方向与前置条件，暂不实施** —— 是否启动"完整 PDS"由用户定夺。若启动，**验收标准**：用 `did:web:...` handle 登录官方 bsky.app，发一条帖子，数据（repo commit）落在自己的 PDS，且被 relay 收录。

## Consequences

优点（若实施）：

- bsky.app 成为发帖 UI：feed、通知、多设备、手机端，体验远超 seal.js；
- 数据自持的"真 PDS"形态，与自托管生态一致（pds.plc.xyz 同款）；
- 互动（likes/reposts）也随 appview 原生可见，弥补"只 log 不展示"的短板。

缺点 / 代价：

- **私钥上 Worker**：推翻 ADR-005 安全模型（Worker 被攻破则帖子可伪造）；单用户可接受，但需用户显式认可；
- 工程量大：会话 + JWT + 密码存储 + 写端点 + MST/commit 服务端构造 + 可变账本迁移 + 导出回 git 备份（ADR-033/034 相关）；blobs（头像/图片）还需 R2；
- 静态资产与活账本双轨期间的一致性问题（seed 迁移、冲突处理）需设计；
- 与"纯 worker、零依赖、低成本"定位（ADR-031 目标形态）方向相反 —— 它更接近参考 PDS 的完整形态。

## 替代方案（对比）

| 方案 | 发帖方式 | 成本 | 数据归属 |
|---|---|---|---|
| **现状**（ADR-014） | seal.js CLI，本地签名 | 零 | 自己 PDS（静态 journal） |
| **本 ADR（完整 PDS）** | bsky.app / 任何客户端 | 大（私钥上 Worker + 写路径 + 活账本） | 自己 PDS（DO 账本） |
| 中间态（不在本 ADR） | Web UI + 浏览器签名（ADR-013 思路） | 中，但签名与账本矛盾仍未解 | 自己 PDS |
