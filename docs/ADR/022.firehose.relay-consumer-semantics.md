## Context

排查"relay 为什么不收录 / 为什么反复重连"时，需要精确知道 indigo relay 对一条坏流到底会做什么。直接从源码确认（`./indigo`，gitignored 本地源码）：

`HandleRepoStream`（indigo/cmd/relay/stream/consumer.go）中，**只有**以下情况会 DROP 连接：

- 帧 / body CBOR 解析失败
- 非二进制 WS 消息
- `sched.AddWork` 错误
- 网络错误

而**每个事件级的验证错误**（`processRepoEvent` → `VerifyRepoCommit`）只记日志并**吞掉**（callback 返回 nil，`sub.UpdateSeq` 照常执行）；乱序 seq 被跳过而非致命（`lastSeq` 每连接从 -1 开始）。

另外两个协议事实：

- **HostChecker 契约**（indigo/cmd/relay/relay/host_checker.go）：`CheckHost` = 恰好一次 `com.atproto.server.describeServer`（PublicOnlyTransport，5s 超时）；**任何** HTTP 错误 → `ErrHostNotPDS` → `requestCrawl` 返回 `HostNotFound`。
- **首 commit 豁免**（`VerifyCommitMessageStrict`）：commit #1（`prevRepo==nil && evt.PrevData==nil`）跳过 MST 反转 —— 纯 commit-only CAR 也能通过 relay 校验。

## Decision

- 以"**可解析性**"为第一优先级：先保证帧能解析（ADR-021），再谈内容验证。
- 把 `requestCrawl` 的响应当作**实时部署健康探针**：我们的 `describeServer` 一 500，relay 立刻回报 `400 HostNotFound: server is not a PDS: API request failed (HTTP 500)` —— 比任何自测都直接。
- 首 commit 阶段允许 commit-only CAR 最小路径（MST 反转被豁免），后续 commit 再带完整 MST。

## Consequences

优点：

- 明确了调试优先级：流"解析干净但验证失败"时连接保持存活 —— 验证失败不是断连信号，先查帧格式再查 commit 编码。
- `requestCrawl` 400/200 成为部署后第一手健康检查手段（配合 check-federation.js）。

缺点：

- 由于验证错误被吞掉，relay 侧几乎不留排错痕迹 —— 我们必须在本地用同样的校验链（`verifyProofs` / 官方 fixtures）自证，不能指望 relay 报错。
