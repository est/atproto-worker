## Context

项目定位是"数据和逻辑分离的纯 Worker"（ADR-031 之后：Worker + Firehose DO + 数据源接缝）。当前 journal 却**随 Worker 静态资产部署**（ADR-024 的决定），导致一个结构性代价：

> **内容变更必须重新部署 Worker。** 发帖流程是 `seal.js post → cp journal.ndjson public/ → commit+push → wrangler deploy → /refresh` —— 每发一帖就动一次 Worker 代码部署，慢、有部署风险、耦合了"数据变更"与"逻辑部署"。

回顾历史：最早就是外部静态托管 + KV 缓存（因 KV 配额/一致性问题迁走，见 ADR-019/024），后改为 ASSETS。但当时的痛点来自 **KV 缓存层**，不是外部托管本身；而 ASSETS 方案又引入"数据与逻辑同体"的新问题。另一个关键技术事实：Worker **无法回环抓自己的 workers.dev 域**（边缘层 internal error），但抓**外部 host 完全正常** —— 之前的 ASSETS-first 是权宜，外部托管反而是本来就更顺的方向。

外部静态托管的天然优势（用户设想）：

- **便宜免费**：GitHub Pages、CF Pages 免费额度对个人 PDS 绰绰有余；
- **git 即备份**：journal 仓库本身就是完整历史（diff、回滚、clone 即恢复）；
- **导入导出方便**：纯 NDJSON 文本，拷贝即迁移；
- **不 vendor-lockin**：任何能托管静态文件的平台都能放，换平台只改一个 URL；
- **挪窝容易**：JOURNAL_URL 是指向数据源的接缝（承接上一轮对 4 个环境变量的评估结论）。

## Decision

- **journal 主源改为外部静态托管**：`load()/refresh()` 顺序从 `ASSETS → JOURNAL_CONTENT → JOURNAL_URL` 调整为 **`JOURNAL_URL → ASSETS → JOURNAL_CONTENT`**（ASSETS 降级为可选 bootstrap seed，仅在外部源不可用时兜底；无外部源的旧部署仍可用）。
- **发布流程改为纯 git**：`seal.js post "内容"` → `git add journal.ndjson && git commit && git push` → Pages 自动构建部署 → `curl /refresh` 或等 */15 cron 拉取。**不再需要 wrangler deploy**。
- **新鲜度**：依赖 CF 边缘对 `JOURNAL_URL` 的缓存 + `If-None-Match`/`Last-Modified` 条件请求控制带宽；Pages 构建部署延迟（约 1-2 分钟）可接受，发布瞬间的 404 由重试或下轮 cron 兜底。
- **信任边界不变**：谁能写 journal 仓库谁就能注入记录（Worker 不验签，ADR-030）—— 与之前"部署管线即根信任"一致，只是从 wrangler 凭据换成 git 仓库写权限。

## Consequences

优点：

- **发帖不再动 Worker**：数据变更与逻辑部署彻底解耦，发布成本从"一次 wrangler deploy"降到"一次 git push"；
- **免费 + 便携**：无平台锁定，GitHub Pages / CF Pages / 任何静态托管任选，搬家 = 改 `JOURNAL_URL`；
- **备份即仓库**：git 历史 + clone 恢复，天然审计（谁在何时发了什么）；
- Worker 更纯：数据源接缝（`JOURNAL_URL`）与未来拆分（DO SQLite / R2）共用同一抽象，blobs 与互动缓存各自再接一条缝即可。

缺点：

- **新鲜度延迟**：Pages 构建 1-2 分钟，发帖后到 relay/appview 可见比 ASSETS 慢一点（个人 PDS 可接受）；
- **外部依赖可用性**：托管平台故障时 journal 不可达（Worker 报 JournalLoadError）；保留 ASSETS 作 seed 可缓解；
- **每次请求仍全量校验**（ADR-027 不变）：fetch 目标从 ASSETS 换成外部 URL，CF 边缘缓存兜住大部分成本；
- 需保证 Pages 对 `journal.ndjson` 的响应带缓存友好的响应头（`Cache-Control`/`ETag`），否则每次都回源。

## 与既有 ADR 的关系

- **取代 ADR-024 的核心决定**（"journal 随 Worker Static Assets 承载"）；其"移除 KV journal 缓存"部分继续有效（见 ADR-031）。
- **ADR-014（CLI 唯一写路径）** 的"发帖流程较慢"缺点得到缓解（无需部署）。
- **ADR-027 / ADR-030 / ADR-031** 不受影响。
