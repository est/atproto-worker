## Context

ADR-023 的每 IP 限流（8 次/分钟）解决了"单个 relay 重连风暴"（源码确认的 indigo slurper 无退避重连），但 code review（2026-08-16）指出它挡不住另两类配额消耗：

1. **多 IP 洪水**：每次连接尝试（无论接受、429 还是 503）都计一次 DO 请求。每 IP 8 次/分钟的限流可被多 IP 客户端（botnet）绕过 —— 1,000 个 IP 理论上每分钟烧 8,000 次 DO 请求，远超免费层约 33K/天预算。
2. **WS 数据消息**：hibernating DO 上**每收到一条客户端消息 = 一次 DO 请求**。`subscribeRepos` 是服务器→客户端单向流，客户端本不应发任何数据消息；旧实现 `webSocketMessage` 只 `console.warn`，一个常开 socket 可无限发消息烧配额。

另外发现：限流记录写在 503 socket 上限检查**之前**（被拒客户端浪费额度预算），且 `storage.get/put` 异常会把 WS 升级变成 500。

## Decision

在 `src/firehose.js` 增加第二层防护：

- **全局连接上限**：15 次/分钟，跨所有 IP 的滑动窗口（DO storage key `ws-attempts:global`）→ 超限 429。多 IP 洪水被总量封顶；
- **WS 消息即关**：收到任何数据消息立即 `ws.close(1008)`（`closeOnUnexpectedMessage`），不再只打日志 —— 每条消息是一次 DO 请求；
- **每 IP socket 上限**：2 个（`MAX_SOCKETS_PER_IP`），防止单客户端占满全局 8 个 socket 的配额槽位；
- **顺序与容错**：限流尝试记录移到所有拒绝检查（426/429/503）**之后**才写入；`safeStorageGet/safeStoragePut` 失败时 fail-open（限流器失效也不阻断合法订阅者）。

## Consequences

优点：

- 单客户端 + 多 IP 两条攻击路径都被总量封顶：最坏 ~15 次 DO 请求/分钟（= 21.6K/天，仍低于预算，且 429 触发 indigo 拨号失败退避会让风暴自终止）；
- 数据消息无法再烧配额（收到即断）。

缺点：

- 429 会被 relay 解释为拨号失败 → 触发 host 离线判定（预期行为，见 ADR-023）；多 IP 场景下第一个触发全局上限的 IP 会连累其他合法连接 —— 15 次/分钟对正常流量（relay 约 0-2 次连接）远未触及；
- fail-open 意味着限流器本身失效时不设防（可接受的权衡：限流是保护配额，不是安全边界）。
