## Context

早期设计把 journal 缓存在 KV（ADR-019，draft）。实践中发现：

- KV 是硬缓存，journal 重建后必须手动 `npx wrangler kv key delete journal --binding JOURNAL_KV` 才能清除旧内容，部署/发布流程极易踩坑；
- ASSETS 本身已是边缘缓存，再把同一份内容塞进 KV 是重复缓存；
- KV 的写入还有免费额度与一致性成本。

同时，Worker 无法 loopback 抓自己的 workers.dev 域名（边缘层 `internal error`），自引用必须走 `env.ASSETS.fetch()`。

## Decision

- **journal 部署为 Worker Static Assets**：`public/journal.ndjson` 随 Worker 一起部署，`load()`/`refresh()` 顺序为 ASSETS binding → `JOURNAL_URL` 兜底（仅外部托管时用）。
- **移除 KV journal 缓存**：`JOURNAL_KV` 命名空间保留，但只存放控制面键：`relay-notify-ts`（定时 requestCrawl 节流，20 分钟）与 `firehose-cursor`（见 ADR-025）。
- 部署后清理一次历史遗留的 KV `journal` 键即可。

> **已过时部分（2026-08-16，见 ADR-031）**：KV 已完全移除 —— 控制面键 `relay-notify-ts`（通知移至 /refresh，不再需要节流）与 `firehose-cursor`（移入 DO storage）均已删除，wrangler.toml 不再有 KV 绑定。Static Assets 承载 journal 的核心决定不变。

## Consequences

优点：

- 完全自包含，不依赖 S3/R2/Pages 等外部静态托管。
- 发布流程固定：`node cli/seal.js post` → `cp journal.ndjson public/journal.ndjson` → commit+push → `npx wrangler deploy` → `curl /refresh`（或等 */15 cron）。
- KV 只剩两个控制面键，语义清晰、额度占用可忽略。

缺点：

- journal 变更必须重新部署（静态资产不可变），发布延迟 = 部署耗时；对个人 PDS 可接受。
- ASSETS 绑定是 CF 平台能力，Vercel 等平台需另寻承载。
