## Context

relay（bsky.network indigo）迟迟不收录我们的 repo，`getRepoStatus` 一直返回 `RepoNotFound`。逐层排查后发现第一个根因是 **commit v3 对象的编码与 atproto 参考实现不兼容**：

- 原实现 `commitToCbor` 把 `data`、`prev` 编码成普通文本字符串，把 `sig` 编码成 hex 文本字符串，并且**签名就是基于这些错误字节**算的。
- indigo 侧 `Commit.UnmarshalCBOR`（indigo/api/atproto/cbor_gen.go）期望 `data`/`prev` 是 CID link（CBOR tag 42 `{$link}`），`sig` 是原始 64 字节。
- indigo `VerifySignature` 会按 cbor-gen 字段序 `(did, rev, [sig], data, prev, version)` 重新编码 unsigned bytes —— 恰好等于我们 `cborEncode` 的 length-first-then-lex 键排序（ADR-004/项目共享实现），所以只要**值类型**对，字节序天然正确。

## Decision

`src/shared.js` 新增规范编码入口 `commitToCbor(commit)`：

- `data` / `prev` → CID link（tag 42，`{$link: cid}`，`prev` 首 commit 为 `null`）
- `sig` → 原始字节（hex 字符串先 `hexToBytes`）
- `rev` → TID 字符串、`did` → 字符串、`version` → 3

`signCommit` / `verifyCommitSig` / `commitCid` / `commitBytes` 以及 Worker 侧 journal 链校验（`src/journal.js`）统一走该编码。**签名必须覆盖规范编码后的字节**。

## Consequences

优点：

- 与 indigo / atproto 参考实现字节级兼容。
- 验证方式（实测）：用我们的编码器重算一个真实 bsky.network commit 的 CID，结果与 CAR root 完全一致；`verifyCommitSig` 能接受真实 commit 的签名（公钥 = `zQ3...` multibase base58 解码后取最后 33 字节，去掉 `e701` secp256k1-pub 前缀）。
- 不再需要"空 blocks"的临时状态，firehose 与 `getRepo` 可以携带真实 CAR blocks（见 ADR-021）。

缺点：

- **journal 必须重新生成**：旧 commit 签在非规范字节上，`verifyCommitSig` 与 Worker 链校验都会失败。实测做法：`rm journal.ndjson .repo-state.json` 后用 CLI 重新 `post`（gitignore 的 journal + 可重建的 state 缓存，重生成无害）。旧 journal 副本（KV/备份）不可复用。
