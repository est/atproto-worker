## Context

Worker 是"无状态、每次请求重建"的设计（ADR-002 事件溯源静态发布）。当前 `src/index.js` 对**每一个 HTTP 请求**（包括 `_health`）都执行：

1. `new Journal(env)` + `journal.load()` —— ASSETS fetch 拉取 journal.ndjson；
2. `validate()` —— 对每个 commit 做一次 SHA-256（`commitCid()`），校验 commit CID 链 + prev 链 + offset 单调性；
3. `index()` —— 重建 byCollection/byUri 内存索引。

Code review（2026-08-16）确认这是两个资源消耗点：

- **CPU**：校验成本随 journal 事件数线性增长。free tier 单请求 CPU 上限 10ms，超过约 200 条事件后普通请求可能超限；
- **配额/DoS 面**：每个请求一次 ASSETS fetch + 全量哈希，攻击者并发打 `/xrpc/_health` 等轻量端点即可放大 worker 请求配额与 CPU 消耗。

## Decision

**保留每次请求全量校验**（不引入缓存），理由：

- journal 是单一事实来源，校验保证"读到的一定是完整且自洽的链"，引入缓存等于引入"缓存与 ASSETS 不一致"的新故障模式（本项目已吃过 KV 缓存过期的亏，见 ADR-019/ADR-024 的教训）；
- 当前 journal 只有 4 条事件，全量校验成本 ~µs 级，远低于 10ms CPU 上限；
- 每次请求重新校验让部署/发布即时生效，无需缓存失效逻辑。

同时把成本封顶在一个确定阈值内：**当 journal 超过约 200 条事件（或实测请求 CPU 接近 10ms 上限）时，必须引入"部署感知缓存"**（校验结果按 ASSETS 版本/etag 缓存，仅在内容变化时重新校验），在此之前保持简单正确。

## Consequences

优点：

- 无缓存一致性问题，发布即时生效，正确性优先；
- 实现极简，无额外 KV/DO 依赖。

缺点：

- 校验成本随 journal 线性增长，是已知的扩展瓶颈；
- `/xrpc/_health` 等轻量端点同样承担全量校验成本（DoS 放大面）。
