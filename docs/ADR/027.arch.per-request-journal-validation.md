## Context

### 背景：这是什么、为什么需要校验

本项目（ADR-002）用一份**静态文件** `journal.ndjson` 作为整个 PDS 的唯一事实来源：所有帖子、点赞、关注等记录以"事件"形式按行追加，本地 CLI 签名后随 Worker 一起部署。Worker 本身**无状态、无数据库** —— 它不保存任何持久化记忆，每次收到 HTTP 请求，都要从这份文件**重新构建**对外服务的全部数据（XRPC 查询、DID 文档、firehose 流）。

一句话：**文件就是一切**。文件对，服务就对；文件坏了，服务就会把坏数据当真的发给所有消费者。所以"每次读取时自证文件的完整性"不是可选项，而是这套架构成立的先决条件。

为了让不熟悉 atproto 的读者理解下面的校验项，先介绍两个概念：

- **CID（内容寻址标识符）**：某段字节内容的"指纹"。本项目用的是 CID v1，结构为 `版本号(1字节) + dag-cbor 编解码标识(1字节) + sha2-256 哈希(34字节)`，通常写作 `bafyre...` 的 base32 字符串。同样的内容永远算出同样的 CID，内容改一个字节，CID 就完全不同。
- **哈希链（tamper-evident chain）**：每条事件都记录"上一条事件的 CID"（`prev` 字段）。于是整条链像区块链一样互相咬合：改掉中间任何一条，它的 CID 变了，下一条的 `prev` 就对不上，再下一条也连锁失效。**历史不可篡改** —— 这是"用静态文件替代数据库"的可信根基。

### 校验了什么（`src/journal.js:validate()`，逐项）

对 journal 里**每一条事件**依次检查：

1. **offset 严格递增** —— 每条事件的 `offset` 是写入时的文件字节偏移。校验要求它单调递增，保证"只追加"语义；firehose 广播游标和 listRecords 游标都锚定在 offset 上，一旦文件被重建导致 offset 变化，游标会静默失效。
2. **事件级哈希链（`event.prev`）** —— 本条事件的 `prev` 必须等于上一条事件的 CID（新格式取 `commitCid`，旧格式取 `cid`）。对不上即"链断了"。
3. **commit 对象 CID 匹配**（新格式 v1 事件） —— 事件里的 `commit` 对象（含 did、version、data/MST根、rev、prev、sig）按 **canonical CBOR 编码**（ADR-020：data/prev 用 CID link、sig 用原始字节、字段序与 indigo 逐字节一致）重新编码 → SHA-256 → 得到 CID，必须与事件声明的 `commitCid` 完全一致。这一步确保"链条声明的 commit 字节"与"实际存的内容"是同一份东西。
4. **commit 级哈希链（`commit.prev`）** —— commit 对象自己的 `prev` 字段必须等于上一条事件的 `commitCid`。这是与第 2 条平行的第二道链，双保险。
5. **旧格式回退（v0 事件）** —— 对没有 commitCid 的旧事件，用 `{op, collection, rkey, record, prev}` 重新计算事件 CID，与 `event.cid` 比对。

**明确不校验的**（各有专门决策）：

- **签名**（sig 真伪）—— 见 ADR-030：Worker 不做验签，信任边界在部署管线；
- **record → MST 叶子的一致性** —— 由 relay 端校验（ADR-020/021/022 的验证链），Worker 侧不重建 MST；
- **CAR blocks 内部结构** —— 只在 `/getRepo` 按需解析（rebuildRepoCar，见 review 加固项），不在此处逐块校验。

校验通过后才构建内存索引（byCollection/byUri），任何一项失败 → 整次加载失败，请求返回 500 与明确错误信息（fail-closed），**绝不带病服务**。

## 为什么每次请求都校验（必要性分析）

1. **无状态架构没有"一次性校验"的落点**。Worker 的内存不跨请求、不跨实例持久；如果"部署时校验一次"，校验结果存哪里？存 KV/DO 又回到缓存一致性的老问题（ADR-019 的教训：KV 缓存过期导致读到旧数据）。文件本身已经是边缘缓存（ASSETS），**读取即是校验，校验即是读取**，两者合并才没有第二个真相源。
2. **文件可以在任意两次请求之间变化**。发布流程是"替换 `public/journal.ndjson` + 重新部署"，资产随时换新。请求 A 发生在部署前、请求 B 在部署后 —— Worker 无法假定"上一个请求校验过，这个就不用"。对部署窗口内混合读到的内容，唯一安全的行为是每次都重新验证。
3. **fail-closed 是防静默损坏的最后防线**。截断的文件、写一半的行、部署时的比特翻转、恶意的注入 —— 哈希链让这一切都在第一笔查询前现形：报 500 而不是把坏数据当真的发给 appview/relay。反过来想：如果跳过校验，坏文件会以"已验证"的面貌进入 `getRepo` 的 CAR 和 firehose 帧 —— 那正是引发 relay 重连风暴、烧穿 DO 配额的那类事故（ADR-021/023）。
4. **成本目前可忽略，且设有明确的再评估阈值**。校验成本 = 每条事件一次 SHA-256（微小对象，约几十 µs）。当前 journal 仅 4 条事件，单请求总校验成本 ~µs 级，远低于 free tier 的 10ms 单请求 CPU 上限。真正的代价随事件数线性增长，因此给出明确触发线（见 Decision）：**超过约 200 条事件或实测 CPU 逼近 10ms 时，引入"部署感知缓存"**（按 ASSETS 版本/etag 缓存校验结果，内容变化才重验），在此之前保持"简单 + 正确"。

## Decision

**保留每次请求全量校验**（不引入缓存）：

- 校验成本封顶在明确阈值内：**journal 超过约 200 条事件（或实测请求 CPU 接近 10ms 上限）时，必须实现部署感知缓存**（校验结果按 ASSETS etag/版本缓存，仅在内容变化时重新校验）；
- 在此之前，每次请求执行 load → validate → index 三步，作为无状态架构下的默认行为。

## Consequences

优点：

- 无缓存一致性问题，发布即时生效，正确性优先；
- 实现极简，无额外 KV/DO 依赖；
- fail-closed：损坏/被篡改的 journal 在服务任何数据之前就被拒绝。

缺点：

- 校验成本随 journal 线性增长，是已知的扩展瓶颈（阈值已定义）；
- `/xrpc/_health` 等轻量端点同样承担全量校验成本（并发攻击时的 CPU/配额放大面，属于已接受的 DoS 暴露）。
