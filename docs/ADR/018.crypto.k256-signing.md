## Context

AT Protocol 规范支持两种椭圆曲线签名算法：

| 算法 | 全名 | 别名 | WebCrypto 支持 | 硬件支持 |
|---|---|---|---|---|
| `k256` | secp256k1 | — | 否 | Bitcoin 生态硬件、云 HSM |
| `p256` | secp256r1 | NIST P-256, prime256v1 | 是 | TPM、Secure Enclave、云 HSM |

**Ed25519 不在 atproto 规范支持范围内。**

签名流程（两种算法通用）：

1. 数据编码为 DRISL CBOR（严格规范化 CBOR）
2. SHA-256 哈希，输出原始字节（非 hex）
3. 对哈希字节签名
4. 要求使用 "low-S" 签名变量（防 ECDSA 签名可锻性）

公钥编码使用 multikey 格式（`did:key` 方案）：

- `p256`：codec `0x1200`，压缩公钥 33 字节
- `k256`：codec `0xE7`，压缩公钥 33 字节

## Decision

使用 `k256` (secp256k1) 作为签名算法。

理由：

1. **atproto 参考实现默认使用 k256**。官方 TypeScript SDK (`@atproto/crypto`) 默认生成 k256 密钥
2. **现有 journal 兼容性**。项目已有的 journal.ndjson 中所有签名都基于 k256，切换算法会导致历史记录无法验证
3. **生态系统匹配**。k256 因 Bitcoin 生态有广泛的库和硬件支持
4. **当前实现使用 `@noble/secp256k1`**（CLI）和自定义 CBOR/CID 实现（Worker），已验证通过 interop tests

p256 的优势（供未来参考）：

- WebCrypto API 原生支持，无需额外依赖
- TPM / Secure Enclave 硬件支持更广泛（非 Bitcoin 生态）
- Cloudflare Workers 的 `crypto.subtle.sign()` 直接支持 p256

如果未来需要迁移到 p256：

- 需要轮换密钥（生成新的 p256 密钥对）
- 重新签名 journal 中所有事件（或创建新的 journal）
- 更新 DID 文档中的公钥
- Worker 侧验证逻辑需要支持双算法

## Consequences

优点：

- 与 atproto 生态默认行为一致
- 无需迁移现有 journal
- `@noble/secp256k1` 库成熟、轻量、无原生依赖
- 通过 atproto interop tests 验证

缺点：

- WebCrypto 不支持 k256，CLI 需要额外依赖 `@noble/secp256k1`
- Worker 侧无法直接用 WebCrypto 验证签名（当前项目不验证签名，只验证 CID）
- 如果 atproto 生态未来转向 p256，需要迁移
