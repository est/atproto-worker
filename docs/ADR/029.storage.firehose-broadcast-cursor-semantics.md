## Context

ADR-025 引入 KV 持久化 `firehose-cursor` 解决"静态 ASSETS 下新事件永远检测不到"的问题。code review（2026-08-16）发现该实现有两个可靠性缺陷：

1. **丢事件**：广播是 fire-and-forget（`ctx.waitUntil(stub.fetch(...))`），**游标无条件推进**。若 DO 广播失败（500、配额、崩溃），游标已越过未广播事件 → 这些事件**永久丢失**，relay 的 repo 与我们的 journal 分叉 → 下一次 commit 的 `prev` 对不上 → relay 丢弃整条流。
2. **回退/重复**：KV 读-改-写非原子。并发 `/refresh` 同时读同一游标 → 重复广播；写慢的请求可能把游标写回旧值 → 已投递事件被重新广播。

另外 `getEventsFromCursor` 默认 limit 100：超过 100 条新事件时只广播前 100 条、游标却推进到第 100 条，剩余事件依赖下一次 refresh（延迟但不丢 —— 但 /refresh 的 `eventCount` 会误报）。

## Decision

`src/index.js` 的 `broadcastNewEvents` 修正为：

- **先 await DO broadcast 响应**，`resp.ok` 才推进游标；失败则记日志、游标不动，事件留给下一次 refresh/cron 重试；
- **游标单调不减**：`nextCursor = max(当前游标, 本批最后一条 offset)`，并发下不会回退（重复广播无害 —— relay 按 rev/seq 丢弃过期事件）；
- **不截断**：直接取 `journal.events.filter(e => e.offset > cursor)` 全量（不再走 100 条 limit 的 `getEventsFromCursor`）。

## Consequences

优点：

- 广播失败不再丢事件（最多延迟到下一次刷新），relay 与 journal 不会因广播失败而分叉；
- 并发 refresh 安全：游标不回退，重复投递被 relay 幂等丢弃；
- 语义简单：游标 = "已成功广播的最大 offset"。

缺点：

- 广播失败时需要等下一次触发（手动 /refresh 或 */15 cron）才重试 —— 对个人 PDS 可接受；
- 一次广播携带全部待发事件（无分页），journal 极大时单次 broadcast 请求体变大 —— 当前规模无碍，若 journal 超千条再考虑分批。
