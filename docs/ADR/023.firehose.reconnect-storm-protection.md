## Context

Durable Objects 免费额度被烧光的根因（源码确认，indigo/cmd/relay/relay/slurper.go `subscribeWithRedialer`）：

- `backoff` 只在 **dial 失败**（`d.DialContext` 出错）时递增并 sleep；
- 成功 HTTP 101 之后流解析/验证失败（返回后走重连）时，**既不 sleep 也不递增 backoff**（backoff 只在 cursor 有进展时重置）；
- 每一轮循环 = 一次 DO 请求（WS upgrade）→ 持续 2-5 req/s → 几小时内烧穿 DO 免费层。

实测（live domain）：relay 在 1 分钟内对单个 IP 发起约 19 次连接，我们的限流器每 IP 返回 3 次 429 后风暴停止（约 2-3 分钟）——indigo 的 dial 失败 backoff（15 次失败 → host 标记 Offline）让循环自终止。

## Decision

在 `src/firehose.js` 加两层防护：

1. **每 IP 滑动窗口连接限流**：8 次/分钟，DO storage key `ws-attempts:<ip>`，120s TTL；超限返回 **429**（非 101）。客户端 dial 失败 → indigo backoff 生效 → 15 次失败后 host Offline → 风暴自终止。
2. **并发 socket 上限**：8 个，超限返回 **503**。

健康状态 = 1 次连接保持打开、约 0 配额消耗；风暴只在我们的流不兼容（帧/CID 编码问题）时发生，修复编码（ADR-020/021）后限流器基本不触发。

## Consequences

优点：

- DO 配额消耗从"数小时烧穿"降到"约 0"。
- 限流器已 live 验证有效（19 连 → 3×429 → 停止）。

缺点：

- 429 响应在 relay 侧被解释为 dial 失败，会触发 host 离线判定 —— 这是预期行为（自终止），但调试期间要小心"我们的流坏了 → 被限流 → 看起来像被拒收"的误导链路。
