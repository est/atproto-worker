## Context

架构演进到"Worker + Firehose DO + 静态资产"三件套后，KV 的三个用途逐一被消解：

1. **journal 缓存** —— 早已移除（ADR-024 的 Static Assets 承载），KV 只剩控制面键；
2. **relay-notify-ts**（requestCrawl 节流）—— 通知频率本可降级：relay 订阅一旦建立就长期保持，重新通知只在新内容发布时需要。把通知从 cron（每 15 分钟）挪到发布动作 `/refresh`（人类触发、罕见），**节流就不需要了**；
3. **firehose-cursor**（广播游标）—— 这个必须跨请求持久，但 **Durable Object 自带持久 storage**，无需 KV。

结论：KV 的三个用途全部消除 → 绑定、配置、额度、`wrangler kv namespace create` 的部署步骤统统可以删掉。

## Decision

- **删除 wrangler.toml 的 `[[kv_namespaces]] JOURNAL_KV` 绑定**，代码中所有 `env.JOURNAL_KV` 引用与相关注释一并移除；
- **广播游标移入 Firehose DO 的 storage**：`/broadcast` 成功广播后持久化 `broadcast-cursor`（max，单调），`/cursor` 端点读出供 refresh/cron 判断新事件（语义与 ADR-029 一致，只是存储位置变了）；
- **requestCrawl 通知移到 `/refresh`**：发布（部署 + refresh）时通知 relay 重新爬取，cron 不再周期通知，无需节流；
- **interactions 保持 log-only**（ADR-015），每次 cron 运行拉取并打日志，不持久化、无节流（结果本就丢弃，节流省的是无意义的外部请求，量级可接受）。

## Consequences

优点：

- 部署面最小化：无 KV namespace 创建/配置/清理步骤，wrangler.toml 更短；
- KV 免费额度（读/写/键数量）的占用与烧穿风险归零 —— 目标形态"少量代码 + DO"；
- 状态全部收敛到一处（DO storage），一致性问题面变小。

缺点：

- 广播游标绑定在 DO 实例的生命周期上：DO 被删除/重置（迁移、手动清理）后游标回到 -1 → 下一次 refresh 全量重放（relay 按 rev/seq 幂等丢弃，安全但多一次广播）；
- relay 通知只在手动 `/refresh` 时发生：relay 把我们标记 offline 后，需发布（refresh）才会重新请求爬取 —— 对个人 PDS 可接受；
- 每次 refresh/cron 广播 = 2 次 DO 请求（/cursor + /broadcast），约 192 次/天，占 DO 月度预算 ~0.6%，可忽略。
