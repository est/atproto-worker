## Context

code review（2026-08-16）指出：Worker 侧 `src/journal.js:validate()` 只校验 **CID 链自洽性**（commit CID 与 commit 对象匹配、prev 链、offset 单调），**不校验 commit 签名**。签名校验只在 CLI（`cli/seal.js validate` / `verifyCommitSig`）执行。

风险：任何能改写被服务 journal 的一方（被攻破的部署管线、JOURNAL_URL 被篡改）都可以重算 CID 链并注入任意记录，Worker 会把它当作"已验证"数据服务给消费者。

为何不直接加验签：

- **WebCrypto 不支持 secp256k1**（只有 P-256/P-384 等 NIST 曲线），Worker 侧做 k256 验签需要引入纯 JS 实现（如 @noble/secp256k1）——新增依赖 + 每请求/每条事件一次验签的 CPU 成本（与 ADR-027 的全量校验叠加）；
- **威胁模型**：journal 由 owner 本人在本地 CLI 签名后部署。能改写 journal 的攻击者要么已攻破 owner 机器（此时私钥同样失守，验签无意义），要么攻破部署管线（wrangler/git 凭据，同样接近完整控制权）。**部署管线本身就是根信任边界**，验签保护的场景与根信任重合。

## Decision

**Worker 不验签 commit 签名**，仅保留 CID 链 + prev 链 + offset 自洽性校验（ADR-010/ADR-027）。签名校验由本地 CLI 在写入时完成（`cli/seal.js validate`，需 config.json 公钥），部署前必须通过。

若未来出现"非 owner 可写入 journal"的部署形态（如第三方托管、多人协作发布），再引入 Worker 侧验签（届时评估 @noble/secp256k1 或平台级签名验证），并同步处理 ADR-027 的缓存问题。

## Consequences

优点：

- 零新增依赖，Worker 保持"无私有材料、纯验证器"的极简形态（ADR-005 私钥仅在本地）；
- 不增加每请求 CPU 成本（与 ADR-027 的扩展性约束不叠加）。

缺点：

- 部署管线被攻破时，Worker 无法识别伪造记录（接受的信任边界）；
- 验签只存在于 CLI，journal 的"真实性"依赖发布流程纪律（validate 通过才部署）。
