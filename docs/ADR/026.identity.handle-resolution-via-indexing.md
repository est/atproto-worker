## Context

早期验证发现 `com.atproto.identity.resolveHandle` 对 `atproto-worker.yiesty.workers.dev` 返回 400，当时结论是"缺少 `_atproto` TXT 记录导致 appview 无法解析"（appview 的 `getDidsByHandles` 不会回退到 did:web 的 /.well-known/did.json）。而 workers.dev 子域名无法托管 TXT 记录，一度以为 handle 解析被 DNS 卡死、必须上自定义域名。

后续排查（ADR-020/021/022 的联邦修复）改变了前提：**问题不是 DNS，而是我们从未被 relay 收录**。

## Decision

- **不做任何 DNS 改动，不要求 `_atproto` TXT 记录**。
- 依赖标准索引路径：relay 收录 repo（requestCrawl → 订阅 firehose → 验证并存储 commit）后，appview 的 identity 目录从我们的 DID 文档 `alsoKnownAs: ["at://atproto-worker.yiesty.workers.dev"]` 学到 handle ↔ DID 映射。
- 验证（Aug 16）：relay `getRepoStatus` 200 active 之后，`api.bsky.app/xrpc/com.atproto.identity.resolveHandle?handle=atproto-worker.yiesty.workers.dev` 返回 200 `{"did": "did:web:..."}`。

## Consequences

优点：

- 免去了自定义域名 / DNS TXT 的部署负担，workers.dev 子域名即可完成身份解析。
- 身份可见性与 repo 索引状态天然一致：收录即解析。

缺点：

- handle 解析依赖 appview 已索引（有冷启动/被移除窗口，如 relay 标记 host offline 期间可能短暂不可解析）。
- 对非 did:web 的外部 handle 仍走 DNS/HTTP 解析路径（`src/did.js:resolveHandle` 的 `.well-known/atproto-did` 与 TXT 分支），本 ADR 只覆盖自有 handle。
