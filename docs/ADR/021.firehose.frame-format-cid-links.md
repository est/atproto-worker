## Context

`subscribeRepos` 的帧格式有两个独立但都致命的坑，导致 relay 连接反复断开、cursor 无法持久化：

1. **帧缺 header**：atproto 帧 = `CBOR(header) + CBOR(body)` 两段。header 形如 `{op: 1, t: "#commit"}`（`FrameType.Message = 1`，`FrameType.Error = -1`），参考实现 `Frame.toBytes() = encode(header) + encode(body)`，解析端 `Frame.fromBytes` 用 `decodeAll` 期望拿到 `[header, body]` 两段。早期实现只发了 body（且 body 里塞了 `$type`），relay 解析直接失败。
2. **body 内 CID 字段用字符串**：`commit`、`ops[].cid`、`prevData` 如果发成普通字符串，indigo 的 `LexLink.UnmarshalCBOR`（`cbg.ReadCid`）会失败 → `HandleRepoStream` 报错断连 → cursor 不推进 → 每次重连都全量 backfill，放大 DO 配额消耗（见 ADR-023）。

## Decision

`src/firehose.js` 的 `formatEvent` 直接返回**完整帧字节**：

- header：`CBOR({op: 1, t: "#commit"})`，错误帧为 `{op: -1}` + `{error, message}`
- body：`CBOR({seq, rev, since, blocks, commit, ops, prevData, ...})`，其中 `commit` / `ops[].cid` / `prevData` 一律用 `{$link: cid}`（tag 42）
- `prevData` = 前一个 commit 的 MST root（`prevMstRoot`），首 commit 为 `null`；`since` 为字符串或 `null`
- 调用方 `ws.send(frameBytes)` 直接发送，不再包一层 `cborEncode`

同时 CLI（`cli/repo.js` RepoManager、`cli/seal.js`）在每次写操作后记录 `prevMstRoot` 写入 journal，供 firehose 取用。

## Consequences

优点：

- 本地 dev :8794 实测 3 帧，header 为 `{"t":"#commit","op":1}`，body 以 `ac 63 6f 70 73`（"ops" map，无 `$type`）开头。
- 与真实 bsky.network 帧 ground truth 一致：`{t:'#commit',op:1}`，`commit/ops[].cid/prevData = {$link}`，`since` 为字符串，`seq` 为大整数，`blocks` 为字节。
- 配合 ADR-020 后，relay 首次能完整解析我们的流。

缺点：

- 改动发生在部署窗口内，曾与一次全端点 500（error 1101）回归时间重合，一度误判为帧修复导致 —— 实际为独立部署问题（本地同工作树 dev 200、部署 500），已另行定位。
- `prevData` 语义对首 commit 与后续 commit 不同，CLI 与 firehose 两端需保持同步。
