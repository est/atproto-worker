## Context

code review / 架构审视时提出的两个问题：(1) 现有 `journal.ndjson` 是否字段冗余、要不要精简；(2) 未来 atproto 升级时这个设计有无隐患。

### 当前一行事件的字段（实测 2026-08-16）

`offset, op, collection, rkey, record, did, rev, recordCid, commit, commitCid, mstRoot, prevMstRoot, blocksB64, prev, prevRev, time`

逐一核对冗余性（对照事件级字段与 commit 对象内部字段，4 条真实事件逐字节验证）：

| 字段 | 冗余性质 | 说明 |
|---|---|---|
| `did` | **完全冗余** | ≡ `commit.did` |
| `rev` | **完全冗余** | ≡ `commit.rev` |
| `mstRoot` | **完全冗余** | ≡ `commit.data` |
| `prev`（事件级） | **完全冗余（v1）** | ≡ `commit.prev`；仅 legacy v0 事件（无 commit）才需要 |
| `recordCid` | **可推导** | = CID(record)，存储免重算 |
| `prevMstRoot` / `prevRev` | **可推导** | = 上一条事件的 `commit.data` / `rev`，跨行反规范化，供 firehose 直接取用 |
| `offset` | **可推导** | 文件字节偏移，供 seq/游标 |
| `commitCid` | **可推导但需显式** | = commitCid(commit)，Worker 校验时重算（ADR-027）；同时是链条引用（`prev` 指向它） |
| `blocksB64` | **大冗余** | CAR = commit + record + MST 节点的重新编码（内容与 `commit`/`record`/`mstRoot` 重复），firehose `blocks` 与 getRepo 直接用它 |
| `record` / `op` / `collection` / `rkey` / `time` | **必需** | 内容本体与路径；`time` 为事件时间（不在 commit 内） |

结论：**约 1/4 字段完全冗余、约 1/3 可推导**，但均为"结构化、可校验"的冗余。

## Decision

### 1. 精简：不做

理由（冗余是**有意为之**，且与既有约束互补）：

- **读时 CPU 换写时体积**：冗余字段让 Worker 读/广播时零重算（`formatEvent` 直接取 `recordCid`/`prevMstRoot`/`prevRev`）。若精简成"推导"，每请求/每广播都要重算 CID、跨行回溯链条 —— 恰好撞上 ADR-027 的"每次请求全量校验"CPU 成本（冗余是省 CPU 的缓存，而 ADR-027 已把 CPU 列为扩展瓶颈）。
- **行自包含**：DO 广播路径按事件数组独立处理，跨行推导会破坏"任意行可独立消费"的性质。
- **冗余不漂移**：`commitCid` 被 Worker 校验（重算比对），`offset` 被单调校验，链条完整性校验兜住了任何不一致 —— 冗余是"验证过的冗余"。
- **体积可忽略**：每行 ~1KB（主要是 blocksB64），个人 PDS 年量级也在 KB-MB，无压缩动力。

**可接受的最小清理（仅在将来做 schema v2 时顺带）**：去掉 `mstRoot`（用 `commit.data`）、v1 行去掉事件级 `did`/`rev`（用 `commit.*`）。**现在不动** —— 动它要同步改 CLI、Worker 校验、firehose、测试四处，收益接近零。

### 2. 未来 atproto 升级隐患

风险评估：

| 隐患 | 等级 | 说明 |
|---|---|---|
| **无 schema 版本标记** | **高** | 事件格式是**本项目自己的格式**，不是 atproto 协议的一部分。一旦事件形状变化（如做存储拆分/写路径时演进字段），旧 journal 无迁移标记，只能靠代码双路径猜 —— HANDOVER 时期规划过的 `_schemaVersion` 方案（首行元数据或 `schemaVersion` 字段 + `cli/migrate.js`）**从未落地**。这是真正的隐患 |
| **commit 版本升级（v3 → v4）** | 中 | `commitToCbor`（ADR-020）硬编码 version:3 与字段序；relay `VerifyStructure` 校验 version。若 atproto 引入 commit v4，需 CLI 支持双版本产出 + Worker 校验双版本读入；旧 v3 记录必须继续可读（方案：validate() 按 version 分流） |
| **firehose 帧演进**（新增事件类型 / 字段） | 低 | 我们只发 `#commit`，relay 消费语义已确认（ADR-022）；新增类型（`#sync`/`#identity`/`#account`）只需按新格式补发，不破坏现有链 |
| **MST / CID / 编码规范变更** | 低 | 均为稳定规范（官方 fixtures 验证过）；read-only 姿态下风险小 |
| **数据源拆分（ADR-032）后** | 提示 | 外部托管 + 未来写路径（DO SQLite 活账本）落地时，正是引入 schema 版本化 + 迁移工具的正确时机 —— 与本次"不动"的结论一致 |

**决策**：保持 journal 字段现状与格式稳定；**在数据源拆分 / 写路径工程启动时，同步落地 schema 版本化**（`_schemaVersion` 元数据 + 迁移工具 + 双版本校验路径），并让 `validate()` 按 commit version 分流以兼容未来 v4。

## Consequences

优点：

- 读时零重算，与 ADR-027 的 CPU 约束一致；行自包含，广播/回填逻辑简单；
- 冗余经链校验兜底，不会漂移；保持格式稳定则无迁移成本；
- 明确了升级路径：隐患收敛为"commit 版本分流"与"schema 版本化"两件事，都有预案。

缺点：

- 冗余字段使行体积略大、视觉上"脏"（可接受的代价）；
- schema 版本化推迟到拆分工程时落地 —— 在拆分之前若需改事件格式，仍会踩无版本标记的坑（预案：拆分时一并解决，期间不改格式）。
