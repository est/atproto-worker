## Context

发布新帖后 relay 一直收不到广播，只在 relay 自己重连时才拿到新数据。根因：

- 旧 `/refresh` 的"新事件"逻辑是把 `load()` 和 `refresh()` 的 CID 做 diff —— 但两者读的是**同一份静态 ASSETS**，永远相同 → 永远检测不到新事件 → broadcast 从不触发。

## Decision

`src/index.js` 的 `broadcastNewEvents()` 改用 **KV 持久化游标**：

- KV 键 `firehose-cursor` 记录上一次已广播的 journal offset；
- `/refresh` 与 */15 cron 都广播游标之后的所有事件，然后推进游标；
- 首次运行游标为 -1 → 回放全部事件（安全：relay 会丢弃过期 rev/seq）；
- 发布后即使没人触发 `/refresh`，cron 也会广播。

> **存储位置已变更（2026-08-16，见 ADR-031）**：KV 完全移除，游标移入 Firehose DO storage（`/broadcast` 持久化、`/cursor` 读取），推进语义（成功后才推进、单调）与 ADR-029 保持一致。

## Consequences

优点：

- 端到端实测通过：post 4 → deploy → `/refresh` 报 "4 events broadcasted" → appview `postsCount` = 4、relay `getRepoStatus` rev 更新、relay CAR root = 新 commit CID；第二次 refresh 报 0（游标已推进）。
- 发布流程与 cron 广播解耦，不依赖 diff 猜测。

缺点：

- 引入一个 KV 写键，发布瞬间 KV 最终一致窗口内可能短暂漏广播 —— cron 每 15 分钟兜底，可接受。
